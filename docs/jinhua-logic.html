jinhua 技能（jinhua skill）运行逻辑

jinhua 把真实任务里的可复用方法沉淀成可验证、可跨项目归并、可由用户确认的技能改进（Skill improvement）。触发层只分类、计数、提醒和去重；核心账本与用户确认门保持独立。

触发时运行自动检查（cycle） 本地纠错判断 + 每 8 轮回顾 弱信号静默忽略 强证据才提案 项目规则 / 增强 Skill / 全局 Skill / 拒绝 / 修订 跨项目只晋升压缩证据

一句话：jinhua 不是记忆库，也不是自动改代码的代理。它是一个“方法论信号蒸馏器”：先静默记录和聚类，证据足够强时才给用户一个小而明确的技能进化提案（Skill Evolution Proposal）。

1

主闭环

触发 任务出现方法信号

用户纠正、成功方法、重复失败、技能规则缺口（Skill rule gap），或用户要求让技能进化。

检查 运行自动检查（cycle）

初始化运行态，读取本地状态，导入全局层，列出待确认门控（pending gates）和已就绪聚类（ready clusters）。

记录 记录信号（log-signal）

只记录可迁移的方法论摘要，包含触发条件（trigger）、方法动作（action）、迁移条件（transfer_conditions）和验证路径（verification_path）。

聚类 本地聚类（cluster）

按方法类型（operator）和方法短名（method slug）汇总同类信号，更新次数、强度、状态和证据样本。

确认 用户门控

只有就绪（ready）后才提出提案（proposal）。用户选择项目规则（project_rule）、增强已有 Skill（skill_patch）、个人全局 Skill（personal_global_skill）、拒绝（No）或修订（Revision），结果写回账本。

2

三道触发闸门

第一道：输入侧本地判断

用户输入后、本轮主模型处理前，用本地规则判断是否在纠正工作流、验证标准、工具或遗漏流程；同时读取就绪聚类和待确认门。它不写经验，也不单独调用模型。

第二道：直接调用与去重

用户明确要求沉淀，或 Agent 发现可迁移方法时，可以当前轮直接进入 jinhua。调用保护门只防同轮重复和循环，不拦第一次有效调用。

第三道：固定 8 轮回顾

按单个会话每 8 个不同用户回合，通过输入侧隐藏上下文向当前正常模型调用加入一次极短回顾，检查本轮及此前对话。同一回合只注入一次，不产生额外模型继续，也不会显示内部 Hook 提示。

3

什么时候安静，什么时候打扰用户

安静路径

单次弱信号、普通偏好、一次性事实、泛泛提示词，不写入账本，也不进入提案（proposal）。

本地就绪条件（ready）

同一项目同类信号达到 2 条时，不看强度，先进入“仅项目规则就绪”，只能提议写入当前项目。达到 3 条信号或强度总和 5 后，恢复完整落点判断。log-signal --immediate 仍是唯一即时通道。

提案路径

已就绪聚类（ready cluster）先产出提案骨架（proposal skeleton）；Agent 再补成具体目标、带标题的完整 Markdown 修改块（patch）和主要风险（risk），占位符不能进入确认门。

选择落点（Placement）

完整就绪时，用户可以选择项目规则、增强已有 Skill 或个人全局 Skill；两条同项目信号触发的提案只提供项目规则、拒绝和修订。选择后，Agent 先用宿主原生工具修改并验证目标，成功后 apply 命令才记录采纳。

拒绝（No）

记录拒绝，聚类（cluster）进入冷却（cooldown）；收到 5 条新的同类信号后才解除，避免反复打扰用户。

修订（Revision）

把修订意见写入拒绝记录，重写提案（proposal），再让用户用同一个门控确认。

4

数据树

jinhua 技能目录（Skill directory）

保存技能指令（Skill instructions）、脚本、参考文档，以及跨项目晋升层。

项目本地：.jinhua/data/

保存当前项目的原始信号（raw signals）、聚类状态（cluster-state）、提案记录（proposals）、已采纳修改（adopted edits）和已拒绝提案（rejected proposals）。采纳项目规则不会清零或停用原信号。

技能全局层（Skill global layer）：<jinhua-dir>/global-data/

只保存压缩后的方法证据和哈希化项目身份，用于判断一个方法是否跨项目重复出现。

稳定入口：scripts/jinhua.py

命令行接口（CLI）只做确定性账本工作：初始化、迁移、记录、聚类、导入、完整提案记录、确认结果记账和验证。所有已写入信号永久保留。

5

跨项目晋升

指纹

优先用方法类型（operator）+ 方法动作（action）形成方法指纹（method fingerprint），触发条件（trigger）和迁移条件（transfer_conditions）作为迁移证据。

项目

至少需要 2 个不同项目。B 项目两条证据先形成项目规则后，C 项目再出现一条同类证据，仍可把三条证据合并为全局就绪。

强度

普通路径仍是 3 个项目、5 条证据、强度 7；新增的跨项目重复路径只要求至少 2 个项目和 3 条证据，不看强度；原强证据快速路径继续保留。

门控

全局晋升也必须展示提案（proposal），并经过带落点的用户确认：增强已有 Skill（skill_patch）、个人全局 Skill（personal_global_skill）、拒绝（No）或修订（Revision）。

6

“更聪明”的具体含义

更会识别

只记录可复用的方法信号，不把普通任务噪音、一次性事实、个人偏好塞进账本。

更会压缩

把不同说法归并为同一个“动作优先”的方法指纹（action-first method fingerprint），减少重复规则。

更少打扰

未达到阈值时只继续任务。达到阈值后只展示紧凑提案（proposal），并直接给出最小有用落点，不让用户自己找目标 Skill。

7

检查命令

下面这些命令必须保持英文，因为它们是可执行接口；中文页面负责解释它们的含义。

python <jinhua-dir>/scripts/jinhua.py --project-root <project-root> cycle
python <jinhua-dir>/scripts/jinhua.py --project-root <project-root> status
python <jinhua-dir>/scripts/jinhua.py --project-root <project-root> global-status
python <jinhua-dir>/scripts/jinhua.py --project-root <project-root> validate

运行原则：脚本保证账本确定性，Agent 负责可迁移性判断和原生编辑验证，用户负责最终风险确认。
